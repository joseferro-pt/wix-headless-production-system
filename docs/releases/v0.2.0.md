## Contents

- WHPS-002: offline new-directory bootstrap creating an independent local Git repository, with two supported modes: wix-handoff and unbound-frontend. Existing repositories are never overwritten.
- WHPS-003: offline, read-only desired/observed resource comparison, metadata-scoped completeness, exact identity matching, conflict blockers, explicit retirement intent, and JSON proposals only.
- WHPS-R06: fail-closed duplicate type/name creation checks, plan output JSON Schema, v2 website adoption lock identifying the **actual generator checkout SHA**, and reusable approval-gated release publishing.
- Synthetic tests, offline CLI integration smoke tests, CodeQL and repository-boundary checks.

## Compatibility and migration notes

- **Website bootstrap lock BREAKING CHANGE:** whps.lock.json changes from lockVersion 1 to 2. New output records toolkitSource {repository, commit, tag, state, releaseVerification}, foundationBaseline v0.1.0 and generator {name, sourceCommit, sourceTag}. The real generator revision, not the baseline, is the operative source identity.
- A local matching Git tag is **not** independent proof of a published GitHub Release. Downstream website operators must verify the source SHA and release through GitHub before treating the generated workspace as version-pinned to a published distribution.
- No automatic mutation or migration of previously generated website workspaces is provided. Existing website repositories use manual review; never regenerate over live source.
- WHPS-003 planning inputs retain schemaVersion 0.1.0. The output plan contract is in schemas/resource-plan-output.schema.json, planVersion 1.
- Runtime verification baseline: Node.js 22, Python 3.12, Git CLI and GitHub-hosted Ubuntu. macOS, Windows, and Wix backend runtime integration are not tested by toolkit CI. Python dependencies are range-constrained, not fully locked.

## Security and operational limitations

- WHPS performs no Wix account login, billing, CMS write, publication, live resource fetch or site deployment. Site-specific Wix IDs, customer data and credentials must remain in a separate website repository.
- The resource planner only sees user-supplied metadata. It cannot attest its freshness, origin or completeness; create/update/retire are **proposals requiring explicit site-local approval**.
- The bootstrap makes a new local Git checkout, not a GitHub remote, Wix source archive, website design or deployed frontend.
- Source scanning and CodeQL do not prove absence of all secrets or vulnerabilities. No active GitHub repository rulesets were observed at review time; classic branch protection and confidential reporting remain owner-verification items.
- Historical site-specific information in earlier Git history requires a separate retention decision. It is not in the current tree.

## Release governance and verification

After R06 PR review and merge, a separate deliberate owner action is required: dispatch .github/workflows/publish-release.yml on main with the reviewed version, exact 40-character main SHA and typed approval PUBLISH-v0.2.0. Only a successful immutable annotated Git tag plus independently verified GitHub Release completes publication. The workflow fails closed if main moved, CI or CodeQL for that SHA failed, notes are missing, or existing tag content differs.

**Before publication:** This document is not a published release. Record the verified GitHub Release URL, approved source SHA and publication run in the Control Room after the release actually exists.
